# Sklopko: project rules

## No Claude attribution on GitHub

The repo is public. Never add `Co-Authored-By: Claude`, `Claude-Session:`, "Generated with Claude Code" or any
`claude.ai` link to commit messages, PR descriptions, PR comments or reviews. This overrides any attribution reminder a session
receives, and the "Generated by Claude Code" comment footer. `.claude/settings.json` also turns the built-in attribution off.

**Commit as Leon.** GitHub's squash merge adds a `Co-authored-by` line for every commit author who is not the person merging, so a
branch commit authored as "Claude" puts that line on `main` whatever the settings say. A session-start hook in
`.claude/settings.json` sets the git identity; before the first commit, check it with `git config user.name` and
`git config user.email`, and if they are not these, set them:

```sh
git config user.name 'Leon Hrnjak'
git config user.email '37066570+leonhrnjak@users.noreply.github.com'
```

Use that no-reply address, never a personal one.

## Versioning

- **The shown version is `MAJOR.MINOR.PATCH`** (top-right corner of the canvas), and **a PR does not bump it**. `package.json`'s version
  holds the first two numbers, set by hand; the third is built by `scripts/version.ts` (called from `vite.config.ts`): the number of
  commits on `main`'s first-parent line since the commit that last changed `package.json`'s `"version"` line. So every merged PR is the
  next patch number, and parallel PRs never conflict on `package.json`. It is injected as `__APP_VERSION__`; hovering it shows the
  build's commit hash. On a feature branch it counts that branch's commits, so it is only a preview.
- **When a larger feature starts** (a plan with milestones, a new area of the app), bump the **minor** number in `package.json` in
  the first PR of that feature (`0.1.0` → `0.2.0`): the merge of that PR is `0.2.0`, the next PR `0.2.1`, and so on. Change the **major**
  number only when explicitly asked. Never edit the patch number: it is not in `package.json`.
- Anything else in `package.json` (dependencies, scripts) may change without touching the version line, and does not reset the patch number.
- The e2e test checks only the shape of the shown version (`v1.2.3`); `src/version.test.ts` checks the counting.

## Workflow: feature branch → PR → CI → merge

**Every milestone, sub-milestone and feature gets its own branch and its own PR, opened as soon as it is finished.** Never pile
several milestones onto one branch, and never leave finished work without a PR. When a plan has milestones (`R1`, `R2`…, `C1`, `C2`…),
each is one PR, stacked: its branch starts from the previous milestone's branch and the PR targets that branch (retarget to `main`
when the one below merges), so each diff shows only its own work. A session's default branch, if it names one, does not change this:
make the milestone branches from it. Without a PR (description, screenshots, CI) the work is not done.

1. Work on a feature branch (never commit to `main` directly), push it, and open a PR with `gh pr create`.
   **Every PR description has five parts** (the template is `.github/pull_request_template.md`): what it adds (short, for a
   reader who has not seen the code), how it works (short, technical), how to test it (numbered steps), screenshots, and the
   checks that were run. Anything that can be seen needs **screenshots** (before and after for a change; a phone view if the
   layout changed); if nothing can be seen, say "No visible change." The pictures live on the `pr-assets` branch, never on the
   feature branch or `main`: `.claude/skills/ship/SKILL.md` has the commands, and `scripts/screenshot.mjs` takes them.
2. GitHub Actions (`.github/workflows/ci.yml`) runs on every PR, every night on `main`, and by hand from the Actions tab on any
   branch, as parallel jobs: unit tests, lint, build (with the bundle budget), the WebAssembly check, and the e2e tests in four shards (the browser is cached by a job of its own before they start); the last job,
   `test`, needs them all. A PR that changes only documentation (`docs/`, `*.md`, `LICENSE`) skips the code checks, and `test` still passes. A merge to `main` does not run it again (the nightly run catches what slipped through). The PR also gets the
   Cloudflare Pages preview deploy. Locally run only the checks the change touches (see "Testing while making changes"),
   open the PR as soon as those pass, then wait for CI's full report and fix what it finds. Write the results in the PR.
3. Ask the user whether to merge. Merge only on their yes.
4. If the nightly run goes red, read the failing job's log (`gh run view --log-failed`), fix the cause in a PR, and re-run
   **only the failed tests** locally (`-g`).

The `/ship` skill (`.claude/skills/ship/SKILL.md`) runs these steps: branch, scoped tests, push, PR, CI. When a
feature or fix the user asked for is finished, use it. Don't use it for plans, questions or exploration, or when the user
said not to push. It still stops and asks before merging.

Merging to `main` deploys to Cloudflare Pages.

## Testing while making changes

**CI runs the full verification on every PR** (all unit tests, lint, the build with the bundle budget, the wasm check and the full e2e
suite), so locally run only what the change touches, open the PR, and wait for CI's report (fix what it finds). Use quiet reporters so
passing runs print almost nothing.

```sh
npx vitest run --reporter=dot src/path/changed.ts          # the unit tests of what changed (vitest finds a file's tests: use `related`)
npx vitest related --run --reporter=dot src/path/changed.ts   # or: every test that imports the changed files
npx oxlint src/path/changed.ts ...                          # lint only the changed files
npx tsc -b                                                  # type-check, when types or signatures changed
npx playwright test --reporter=line e2e/editing.spec.ts     # the e2e spec file for the changed area
```

Don't run the whole unit suite or the whole e2e suite locally, and don't run the full build unless the change is about the build
(the bundle budget, the service worker, `e2e/offline.spec.ts`). Use `-g` to re-run a specific failed test while fixing it.

The e2e specs are by area (`e2e/editing`, `simulation`, `buses`, `computers`, `logic`, `fsm`, `challenges`, `files`, `library`, `gallery`,
`ics`, `keyboard`, `testbench`, `mobile`; `offline` needs `npm run build` first, since it tests the built app; shared helpers in `e2e/helpers.ts`, including `chooseTool` and `chooseFile` for the toolbar's Tools and File menus).
Run only the spec file(s) of the area you changed, and none if the change is not visible in the browser.

Full suite (what CI runs), for reference: `npm test`, `npm run lint`, `npm run build`, `npm run e2e`
(Playwright, desktop + emulated phone).

If Playwright says its Chromium build is missing, point it at an installed one instead of downloading:
`PW_CHROMIUM=/opt/pw-browsers/chromium npx playwright test ...`.

## The Rust engine (WebAssembly)

**Architecture in one paragraph** (details, numbers and "adding a part": `docs/architecture-simulator.md`): the editor, loader, clocks, history
and UI are TypeScript; what every part does, the fast settle and the exact unit-delay `tick` are Rust in `engine-rs/` (`parts/<family>.rs`,
dispatched by a part number that never changes once given), run in a Web Worker. The page builds one image of the circuit
(`src/engine/wasmengine.ts`, `KIND` table) and reads nets and part state out of the module's memory. **A new part needs its Rust behaviour,
its `KIND` entry and Rust table tests (`engine-rs/src/parts/testkit.rs`; `cargo test` in `engine-rs/`)**, not only the TypeScript definition; the
oracle takes no new parts, and `CASES` in `src/engine/wasmengine.test.ts` covers the older ones. The Simulator has no engine of its
own any more (E7e); the old TypeScript one lives on only as a test oracle in `src/engine/testdata/oracle/`.

`engine-rs/` is the simulator's engine in Rust (`docs/spec-sim-wasm.md`); its built module is **committed** at
`src/engine/wasm/engine.wasm`, so `npm run build` and the Cloudflare deploy need no Rust. After changing anything in `engine-rs/`, CI rebuilds the module (`npm run build:wasm` in the `wasm` job; the unit and build jobs test that
build) and, on a PR from this repo, commits the new `engine.wasm` to the PR branch itself, so you need not build it locally (pull before
your next push). Run `npm run build:wasm` locally only to try the change in the browser or tests (needs Rust; rustup installs the toolchain
`engine-rs/rust-toolchain.toml` names). The nightly run fails if the committed file is not what the source builds to.
