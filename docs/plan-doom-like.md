## Why, and what "Doom" means here
Leon asked how close we are to running Doom now that the Rust/WebAssembly engine runs the `cpu6502` board at the real 1 MHz. The real
Doom needs a 32-bit CPU and megabytes of RAM and is out of reach (assessment, "What Doom can mean"). This spec is for a **Doom-like**:
first-person raycast walls with distance shading, doors, a few enemies drawn as scaled sprites, a gun, one small level, on a 6502 board
whose every part is visible. It is the long-running joke of `plan-raycaster.md` finally done on the right machine, and it exercises the
simulator's new speed.

## Decisions (made here, so the milestones are not open)
1. **We write our own engine.** Not a port. VIC Doom (Kweepa) shows no licence on its page; Wolf64 is "strictly non-commercial"; both
   assume a specific video chip. The repo is MIT and going public, so no code from either goes in. They are read as published
   techniques only. The game gets its own name, map and art; nothing from id Software is used (`Sklopko Doom-like` is a working title).
2. **The CPU is the `cpu6502` part in 65C02 mode** (for `STZ`, `BRA`, `PHX`/`PHY`, `INC A`, `(zp)`), at 1 MHz, and only that: Leon decided the
   game does not target the 6502 built from our own parts. The engine is not tuned to NMOS-only quirks.
3. **Assembly, in our own assembler** (`asm6502`), no C compiler. Tables (sine, reciprocal, wall height, sprite scale, quarter-square
   multiply) are generated by a TypeScript script at build time into the ROM image, as `scripts/basic/` does for BASIC.
4. **A reference raycaster in TypeScript is the oracle.** Integer-only, same tables, same rounding: the assembly's picture must equal it
   byte for byte at every tested position and angle (the pattern of `raycaster.test.ts`).
5. **Video through a port, not the address space.** The framebuffer lives inside the part; the CPU sees an address register that counts
   up on every access and a data register (the X16 VERA and TMS9918 way). It costs 3 to 4 bytes of the 64 KB, not 8 KB.
6. **Banking with the parts we have.** The window at `$8000–$BFFF` shows one of two 16 KB ROMs, picked by one bit of a latch the CPU
   writes; the ROM at `$C000–$FFFF` is fixed (engine core, vectors). A data-bus multiplexer already picks "RAM or ROM" on the big
   board; it gets one more input. No new mapper part, the circuit is readable, and the ROM part stays at 16 KB (so the hex-text cap
   does not move). Fallback if the board gets too big to read: one 32 KB ROM and a smaller device block.
7. **The engine's size budget** (the rule that stops the scope growing): five levels (16×16 maps, about 400 bytes each), two enemy types, one weapon, no
   textures in the first game (walls are flat colours shaded by distance and side); textures and a richer HUD are the optional D4b and D4c, a ROM of at most 48 KB, RAM of at most 16 KB.
8. **The screen is 160×100, 16 colours (4 bits a pixel, 8,000 bytes)**, a fixed palette. The engine casts 80 or 160 columns, whichever the
   D0 numbers allow.

## The computer (proposal; D2 fixes it)
Ben Eater's map, extended. The device block `$4000–$7FFF` is split by A12/A13 into four 4 KB slots:

| Address | What | Decoded by |
|---|---|---|
| `$0000–$3FFF` | RAM, 16 KB | A15 = 0, A14 = 0 |
| `$4000–$4003` | video port: `VADDR_L`, `VADDR_H`, `VDATA` (auto-increment), `VCTRL` | A14, slot 0 |
| `$5000` | gamepad register: up 1, down 2, left 4, right 8, A 16, B 32 (read) | slot 1 |
| `$5001` | ROM bank latch (write; bit 0 picks the ROM seen at `$8000`) | slot 1 |
| `$6000–$600F` | 6522 VIA: its timer 1 is the frame tick (IRQ) | slot 2 (Eater's address) |
| `$8000–$BFFF` | banked ROM window (bank 0 or 1) | A15 = 1, A14 = 0 |
| `$C000–$FFFF` | fixed ROM: engine core, tables, vectors | A15 = 1, A14 = 1 |

The reset vector and the interrupt routine are in the fixed ROM, so a bank switch never pulls the code from under the CPU.

## What the simulator lacks, and which milestone closes it

| Gap (from the assessment) | Closed by | How |
|---|---|---|
| Only a 16×16 screen, one pixel at two register writes | **D1** | A framebuffer part with a 160×100, 16-colour buffer in the Rust module's `Shared` bag, an auto-increment port, drawn on a canvas in one pass |
| No fast way to draw a wall column | **D1b** (if D0 says so) | A command register: x, top, bottom, colour; the part fills the column |
| ROM cap of 16 KB, no bank switching | **D2** | Two banked 16 KB ROMs and a fixed one, selected by a latch and the existing data multiplexer; `romImage` learns a multi-image build |
| The big board allows only the terminal, VIA and LCD together | **D2** | The board builder takes a `game` device set (video, gamepad, bank latch, VIA); saved circuits and every existing example keep working (their tests prove it) |
| Gamepad only on the small board | **D2** | A read-only register at `$5000` driven by the existing gamepad part |
| No frame timer for pacing | **D2** | The VIA's timer 1 and the CPU's IRQ pin, both existing |
| No multiply | **D0/D3** | Quarter-square tables (about 1 KB); a hardware multiplier part only if D0 shows tables are too slow |
| Step-back history cannot keep up with a framebuffer | **D2** | The game board runs without history (the per-circuit switch from B2); documented in the example's description |
| Assembler has no macros or includes | **D0** | Not needed: the build script concatenates sources and generates tables. Recorded if D0 finds it painful |

## D0 The spike (no app change)
The unknown that matters is the cycles a frame. D0 answers it before any part is built, like `plan-raycaster.md` M1e and BASIC's B1.
- `src/model/doom/reference.ts`: the integer raycaster (map, DDA, tables, wall heights, shading) rendering into a 160×100 array.
- `src/model/doom/engine.s` plus a build script that makes the tables: the same renderer in 65C02 assembly, run on the bare core
  (`newCpu(true)`) in a test harness that exposes a fake memory-mapped framebuffer, as `basic-harness.ts` does.
- Measured and recorded in this doc, for 80 and 160 columns: cycles a frame (walls only) with (a) per-pixel writes through the video
  port and (b) a column-fill command modelled in the harness; the ROM bytes used.
- The version bump (`0.4.0` → `0.5.0`).
- **Done when:** assembly and reference give the same picture at 20 positions and angles, in a unit test; the measured table is in this
  doc; and the **gate** is decided in the PR with Leon: **(1)** if walls take at most 60,000 cycles a frame (about 15 fps at 1 MHz),
  go on without a column fill; **(2)** between 60,000 and 120,000, D1b is added, and the screen drops to 80 columns if needed;
  **(3)** above 120,000 after both, stop and rethink (smaller screen, hardware help) before building D1.

### D0 result (measured, 20 poses, `src/model/doom/doom.test.ts`)
The spike is a 65C02 program of 440 bytes of code and about 3.7 KB of tables (quarter squares 1 KB, ray set-up per angle 1.5 KB, the map 256 bytes
and the rest), run on the bare core. It draws the same picture as `reference.ts` at all 20 poses, for 160 and 80 columns, through the port and by
fill. Walls are in steps of 4 pixels in height (25 levels), which keeps every run on a whole byte.

| Columns | Rays only | Rays + port writes (whole column, sky and floor too) | Rays + column fill |
|---|---|---|---|
| 160 | 122,800 cycles (96k to 160k) | 178,900 (152k to 215k) = 5.6 fps | 130,300 (104k to 166k) = 7.7 fps |
| 120 (screen 120×100) | 92,100 (72k to 120k) | 134,200 (114k to 162k) = 7.5 fps | 97,700 (78k to 125k) = 10.2 fps |
| 80 | 61,500 (48k to 80k) | 117,600 (105k to 136k) = 8.5 fps | **65,400 (52k to 83k) = 15.3 fps** |

What the numbers say:
- A ray costs about 770 cycles and most of that is set-up, not stepping: the 20 poses average only 2.5 DDA steps a ray. Estimated per ray, the four
  quarter-square multiplies for the first edge distances are about 280 cycles, the rest of the set-up about 150, one DDA step about 55.
- Per-pixel drawing through the port is as costly as the rays (a whole 80-column frame is 56,000 cycles of `STA`), so the column fill pays.
- **Gate:** 160 columns is above 120,000 even with the fill: out. 80 columns with the fill is 65,400 on average, 83,000 at worst: **band 2**
  (60,000 to 120,000), so D1b is in and the screen is 80 columns wide. Cheaper set-up (a sparse reciprocal-times-fraction table instead of the
  multiplies) could bring it under 60,000; that is a D3 optimisation and not needed for the gate.
- **120 columns** (asked in review) is a 120×100 screen, since 160 is not a whole multiple of 120: mean 97,700 cycles with the fill (10 fps), worst pose 124,700 (8 fps). That is band 2 on the mean, just over the line at the worst pose. The framebuffer is 6,000 bytes (80 columns: 8,000 on a 160-wide screen, 4,000 on an 80-wide one); the ROM is the same size, only the step table values differ.
- **Decision (Leon, 2026-11-01): 160 columns, 160×100, against the gate's advice.** At 160 columns with the fill the game runs at about 7.7 fps (130k cycles mean, 166k worst, about 6 fps) until the ray set-up is made cheaper. D1b stays in. The milestone that tunes the engine (D3) has the target of getting the mean under 120,000; if it cannot, the width is revisited then.
- The model: the fill takes no time on the part's side; the framebuffer is stored column by column (a column is 50 bytes), which makes a column
  one run of the auto-increment port. D1 should store it that way (the canvas transposes it).

## D1 Video
- A part `Framebuffer 160×100` (name to settle in the PR): pins `CLK`, `WE`, `RS0`, `RS1`, data `D0–D7`, `RST`; the registers of the table
  above; 16 fixed colours. Reads auto-increment too. Out-of-range addresses wrap.
- Rust behaviour in `engine-rs/src/parts/` (family `io`), a number appended in `parts/mod.rs`, a `KIND` entry in `wasmengine.ts`, a
  `CASES` entry in `wasmengine.test.ts`, the TypeScript definition and pin data. The buffer is read back by `syncOut` only when the
  canvas draws; the canvas redraws at display rate from a snapshot, never one SVG node a pixel.
- An example: a small board draws a pattern and a test card through the port.
- **Done when:** the `CASES` lockstep test passes; a unit test draws every colour and an address wrap; an e2e test opens the example and
  sees the test card; the page draws at 30 frames a second while the CPU runs at 1 MHz without dropping the CPU below 900 kHz
  (measured headless, recorded in the PR; the budget in `docs/spec-sim-evals.md` style); the startup chunk does not grow (the part
  and its canvas load on demand).

**What it did, and where it differs from the spec (D1, PR pending).**
- The part is `video` (`Video 160×100`), kind 61 in the Rust module, with the board's chip pins instead of the spec's `CLK/WE`: `PHI2`, `RESB`, `CS0`, `CS1B`, `RS0`, `RS1`, `R/W`, `DI0–7` in, `D0–7` out, answering at the rising edge of Φ2 like the terminal and the VIA. Registers: 0 `VADDR_L`, 1 `VADDR_H`, 2 `VDATA` (read or write at the address, then count up), 3 `VCTRL` (bit 0: hold the address; writing bit 7 clears the screen). Reset clears the registers, not the picture.
- The picture is 8,000 bytes in the module's `fb` array, column by column, 50 bytes a column, the upper pixel in the high nibble. An address is taken modulo 8000, so it wraps. 16 fixed colours (`src/engine/videopalette.ts`, our own palette).
- The canvas (`src/ui/VideoCanvas.tsx`) is loaded on demand and draws at most 30 pictures a second from the part's state; the symbol is the canvas, there is no separate inspector section.
- The board builder gets a `video` device (alone on the big board, at `$4000–$4003` repeated), and the example `6502-video` draws a test card. D2's game board will take the chip over with the other devices.
- Measured headless (Chromium, the example with an endless animating tail so the picture changes all the time): 27 canvas draws a second, the CPU at 1 MHz (921 kHz before the draw limit was added, 100% after). The startup chunk is 69.6 kB gzip, no growth.
- Tests: `CASES` lockstep entry, `src/engine/video.test.ts` (every colour, the wrap, readback, hold, clear, the example's card), and `e2e/computers.spec.ts`.

## D1b Column fill (conditional)
- A command register: write x, top, bottom, colour; the part fills the column in one evaluation. A mode flag keeps plain port writes
  unchanged.
- **Done when:** the unit and lockstep tests pass, and the D0 harness numbers are re-measured on the real part and match the model.

### D1b result
The part gained two pins, `RS2` and `RS3` (16 registers, `$4000–$400F` on the board; the plain port at 0 to 3 is unchanged and an unwired RS2/RS3 is 0).
Registers 4 to 10: `x`, `top`, `bottom`, `colour`, `width`, `sky`, `floor`. **Writing the colour starts the fill**: `width` columns from `x` (wrapping past 159),
each sky down to row `top`, the colour down to row `bottom`, floor below. After reset the width is 1 and the others 0; all read back. This is the register
layout the D0 harness modelled (`CMX` to `CMW`), plus the sky and floor colours, which the harness had as constants. The nibble order is the part's (the even row in the high nibble); D0's
walls are whole bytes, so its pictures did not change.
Re-measured: `doom.test.ts` runs the D0 fill program (160 columns) on the real part in the Rust engine at 4 poses. The picture equals `reference.ts`, and
it is not yet complete 1,500 cycles before the cycle count the model measured and is complete at that count: the fill costs the CPU nothing beyond the five or six `STA`s
per column the model already counted, so the D0 table (130,300 cycles mean for 160 columns) stands.

## D2 The game board
- `board6502.ts` gets a `game` option: video, gamepad register, bank latch, VIA (frame timer, IRQ), 16 KB RAM, three 16 KB ROMs.
- `romImage` takes a list of images; the build script produces the three ROMs; the data multiplexer gains the bank input. The ROM
  data loads on demand (a generated module like `basic-rom.ts`), so the startup chunk does not grow; any growth needs Leon's yes to
  raise the 188 kB budget.
- A test program in the banked ROM prints a bank-0 and a bank-1 byte through the video port, and a timer-driven counter proves the
  frame interrupt.
- **Done when:** a test boots the board, switches banks, reads the gamepad bits, and takes 60 timer interrupts at the right cycle
  counts; every existing board test and example still passes unchanged; the board runs without step-back history; an e2e test
  opens the example in the browser and sees the bank-switch output.

### D2 result
`board6502Builder` takes `game: true` (with `memory: 'big'`; no `devices`). The map is the spec's: video chip `$4000–$400F` (its chip select is A14 and not A13 and not A12, so it no longer repeats
through the block), gamepad register `$5000` (read), ROM bank latch `$5001` (write, bit 0), VIA `$6000`, RAM `$0000–$3FFF`, banked ROM `$8000–$BFFF`, fixed ROM `$C000–$FFFF`.
Wiring: the address splitter now cuts A0–A11, A12, A13, A14, A15; a 4-input AND gives the gamepad/latch slot and a 3-input AND the latch's load strobe; a bus multiplexer picks bank 0 or 1 by the latch
bit into the existing ROM input of the memory multiplexer, and a second one picks video, gamepad or VIA by A12/A13. The banks are the options `banks` (hex) or `bankSources` (assembly beginning at `$8000`);
`rom` or `source` is the fixed ROM. Differs from the spec: `romImage` is unchanged (a new `bankImage` makes the banked images, which have no vector), and the ROM data is not yet a generated on-demand
module, because D2's test program is a few dozen bytes inline in `programs6502.ts`; the game's ROM build script and its generated module come with D3, when there is a real engine.
`gameboard.test.ts` (Rust engine): the same address gives different bytes in the two banks and both reach the video chip; the six gamepad bits read back at `$5000`; the VIA timer, loaded with 16,665,
interrupts every 16,667 cycles (59 interrupts after 59 × 16,667 + 800 cycles, 60 after 60 × 16,667 + 800). The example `6502-gameboard` runs without step-back history; its e2e test sees the two banks' bars.

## D3 The engine on the board
- The D0 renderer, hardened: map, collision, strafe and turn, door opening, distance and side shading, frame pacing from the VIA timer.
- **Done when:** on the board, the picture equals the reference at the 20 test positions plus after a scripted walk (a recorded
  gamepad sequence); a headless run holds the frame rate the D0 table promised (within 25 percent); an e2e test walks to a door and opens it.

## D4 The game
- Two enemy types (patrol and chase), scaled sprites with a depth buffer per column, a weapon with hit tests, health, five 16×16 levels
  in the banked ROM, each with a start, doors and an exit that loads the next, a win and a lose screen, and a HUD strip (health, ammo, level). Art is our own, drawn as tables.
- Example `6502-doomlike` with a description saying the clock, the key map and the expected frame rate.
- **Done when:** a scripted run (recorded gamepad input) kills both enemy types, takes damage, and reaches the exit of each of the five levels, in a unit test on
  the bare core and in an e2e test on the board; ROM size is at most 48 KB; the frame rate with enemies on screen is recorded in the PR.

## D4b (optional) Textured walls
- 16 or 32 pixel-wide wall textures (two or three kinds), 4 bits a pixel, in ROM. Per-pixel texture lookups cost about 10 more cycles a
  pixel, which the budget cannot take with plain writes, so this likely needs a **textured column command** in the video part (x,
  top, bottom, texture, texture column) on top of D1b. D4b is built only if the D4 frame rate leaves room, and the PR says which way it went.
- **Done when:** the textured picture equals the reference renderer at the 20 test positions, and the frame rate with enemies on screen is
  recorded; if it falls under 10 fps at 1 MHz the milestone is dropped and the spec says so.

## D4c (optional) A HUD with a face, and more enemy frames
- A face widget that reacts to health and damage (about 5 frames), a weapon sprite with a fire animation, and 3 to 4 walk and attack
  frames per enemy plus a death animation. Art is our own.
- **Done when:** the frames are shown in a scripted run (walk, attack, die; take damage, face changes), unit-tested against the
  reference, and ROM stays at most 48 KB.

## D5 Polish
- A reference page (Tools), a README line, a phone layout check (the gamepad's touch buttons), a note in the architecture doc, and the
  final frame-rate table in this doc. No new features.
- **Done when:** the phone e2e spec plays the first ten seconds; the docs match the code.

## Risks
- **The cycle estimates may be wrong by 2 times either way.** That is what D0 and its gate are for; a stop at D0 costs one PR.
- **Board builder churn.** D2 touches the builder that the BASIC, VIA and LCD examples use. Mitigation: a new `game` option, existing
  options untouched, all existing tests are the regression suite.
- **Drawing cost in the page.** A 160×100 canvas 30 times a second through the worker's snapshot path is untested. D1's done condition measures it before D3 depends on it.
- **Startup budget.** All new code (part definition, canvas, ROM data, example) must load on demand. If the startup chunk grows at all, stop and ask for the budget.
- **Scope.** Fixed by decision 7: five levels, two enemies, one weapon, no textures in the core game. Textures and the richer HUD are the optional D4b and D4c; music and more levels are a later spec.
- **Licences.** No third-party code or art. If a technique from VIC Doom or Wolf64 is used, it is re-derived from the idea and noted in the PR.
- **Playable on a phone?** A 1 MHz simulation may run slower on a phone; the game then runs in slow motion and stays correct. D5 states this on the example's page.
